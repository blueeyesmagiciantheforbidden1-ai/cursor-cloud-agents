# Durable provider credential broker

`agent_hub/cloud_credential_broker.py` is a concrete standard-library Google REST adapter. It implements acquisition, lease validation/renewal, opaque credential retrieval, refresh publication, release and quarantine. It does not log in, refresh provider credentials itself, start a provider, perform inference, provision cloud resources or expose an HTTP service. Deployment integration is still required.

The fixed project is `project-0c6d31fa-509e-4116-a2c` (`496481413971`), region `us-central1`, Firestore database `runcrew-provider-auth`. No argument can select another project, database, arbitrary host, secret or job. The broker rejects `(default)`, `runcrew-hub` and `runcrew-auth`; there is no fallback. Runtime authentication uses only the attached service account's metadata access token, held in memory. There is no ADC/key-file discovery, environment credential export or redirect following. See Google's [workload authentication documentation](https://docs.cloud.google.com/compute/docs/access/authenticate-workloads).

## Ownership and enrollment

A protected `ProfileConfig` supplies provider, owner profile, the existing owner allowlist hash, a separate canonical account fingerprint, exact secret ID and exact job ID. Allowed secret names are `runcrew-credential-{provider}-{profile}`; jobs are `runcrew-worker-{provider}` or `runcrew-worker-{provider}-{profile}`. Profiles are `ryan` and `blueeyes`; providers are the five existing agents.

`canonical_identity_ref(provider, issuer, subject, tenant)` hashes a versioned deterministic JSON identity. Obtain the immutable subject and tenant from authenticated provider metadata during enrollment, independently of a task, email-only hash or credential filename. The function hashes evidence; it cannot authenticate that evidence. Keep its source receipt private. Do not invent a subject where a provider has not supplied one. Re-enrollment/account changes require explicit operator reconciliation.

One control document per provider plus canonical fingerprint lives in `runcrew_provider_credentials`. Profile aliases therefore cannot create independent locks for the same account. Every read checks the entire immutable binding against protected configuration. A missing or mismatched document blocks acquisition; there is no automatic enrollment. `initialize_binding(exact_version, enrollment_receipt_ref)` is an explicit operator action: it verifies the existing exact secret payload's integrity and creates the control document with `exists: false`. It cannot overwrite a previous enrollment and does not infer its owner from credential bytes.

## Lifecycle

```text
idle --CAS acquire--> leased --CAS intent--> committing
  ^                                            |
  |                     exact Secret Manager version + checksum round trip
  |                                            |
  +--CAS release after durable ack-- committed <-+

uncertain refresh/write --> quarantined --> separately verified reconciliation
```

1. The trusted controller persists a unique 32-character UUID hex request ID before each native launch, then calls `acquire(execution, request_id)`. The broker verifies the configured Cloud Run execution's immutable UID and single-task shape, acquires a monotonically increasing fence, and returns a `Lease`. Its opaque `auth_bytes` is excluded from `repr`; never serialize the whole lease to logs or a tool response. Retrying the same acquisition is permitted only before any native process starts. The ID must not authorize a second process.
2. Pass that same lease object and broker to the package's `credential_state.RefreshSession`. `restore()` requires a fresh private home and writes only its provider credential file. Copilot uses `.copilot/config.json`; Grok uses `.grok/auth.json`. Credentials remain opaque bytes. The broker accepts at most **64 KiB**, the Secret Manager limit, even though older package helpers accept 256 KiB. Oversized credentials fail before publication. See [SecretPayload](https://docs.cloud.google.com/secret-manager/docs/reference/rest/v1/SecretPayload).
3. Keep the trusted controller outside provider task control. Renew well before the configured deadline (default 180 seconds, permitted 30–600). Stop the native process if validation or renewal cannot be confirmed. The provider performs any native refresh itself. A credentialed read-only metadata call can also refresh, so it needs this same lifecycle.
4. Stop and reap the native process before `RefreshSession.finish(native_stopped=True)`. The broker first records a unique commit intent and SHA-256 digest using Firestore `updateTime` CAS. It issues at most one `addVersion`, checks the server checksum acknowledgement, re-reads that exact numeric version and verifies its bytes, then publishes it by CAS. Unchanged bytes reuse the existing version. There is no `latest`, listing, guessed version, automatic refresh or blind retry. Google documents the [atomic commit](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/commit), [precondition](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/Precondition), [addVersion](https://docs.cloud.google.com/secret-manager/docs/reference/rest/v1/projects.secrets/addVersion) and [access](https://docs.cloud.google.com/secret-manager/docs/reference/rest/v1/projects.secrets.versions/access) contracts.
5. Release requires the published durable commit. Lost Firestore acknowledgements are resolved only by a fresh exact-state read. An uncertain Secret Manager mutation is quarantined and never retried automatically. Preserve the refreshed private local bytes for reconciliation where the runtime remains available. Neither a timeout nor a failed quarantine write frees the account; the previous leased/committing state still blocks a successor.

The fence is a control-plane ownership check, not a provider-enforced revocation. **An expired lease never permits takeover.** A previous container could still refresh its token. `reconcile_commit(fence=..., lease_id=..., candidate_version=...)` is separately authorized operator work. It requires the recorded Cloud Run execution UID to be terminal with no running task, and the explicitly identified candidate version's bytes to match the durable intent digest, before one CAS publishes and releases. The [Execution resource](https://docs.cloud.google.com/run/docs/reference/rest/v2/projects.locations.jobs.executions) supplies these lifecycle fields. Missing intent or unrecoverable refreshed bytes requires fresh enrollment after verified termination, not reuse of an old token. The module deliberately has no automatic recovery for that case.

After a successful commit/release, the acquisition CAS also rejects a new request ID from that same recorded execution UID (`execution_already_consumed`). A new execution may acquire after the safe release. Active-lease retry, renewal and commit are unchanged. This is an **immediate reuse guard**, not global exactly-once execution: the control document remembers only the most recent execution, so it does not itself prevent `A → B → A` if the old A remains alive and an outer caller authorizes it again. The trusted controller publishes only intended execution grants, and the service/supervisor must enforce one acquisition/native-launch lifecycle. A lease, request ID or Cloud Run identity is not proof of which native process ran. No history collection or broader IAM permission was added for this check.

## IAM and process boundary

`cloud_credential_foundation.py` in the operator artifact directory prepares this database boundary. `plan` is offline; `provision --execute` first verifies the fixed Google project/account/billing target, then journals exactly four mutations: create the Standard/Native `runcrew-provider-auth` database in `us-central1` with deletion protection, create `runcrew-credential-broker`, create the custom role `runcrewCredentialState`, and bind it to that service account with the condition `resource.name=="projects/project-0c6d31fa-509e-4116-a2c/databases/runcrew-provider-auth"`. The custom role contains only `datastore.entities.get` and `datastore.entities.update`. Initial credential enrollment and immutable execution-grant creation remain separate trusted-controller operations. The helper creates no provider secret, provider identity, Cloud Run service or job.

`status` verifies recorded resource identity/configuration and direct project IAM bindings. If a mutation acknowledgement was lost, it reports observed resource presence without adopting it, clearing intent or retrying. Existing unjournaled resources, changed service-account UID, expanded role permissions, broad broker access, or known gateway/dashboard/task-worker database grants that cross the existing hub/auth boundary stop provisioning. This direct-project check is not an audit of inherited organization/folder policy. `test_cloud_credential_foundation_offline.py` exercises synthetic creation/grant uncertainty and scope failures without contacting Google.

The separate database keeps gateway/dashboard `runcrew-auth` permissions away from provider fences and execution grants. Google supports [database-specific IAM conditions for REST access](https://docs.cloud.google.com/firestore/native/docs/manage-databases#configure_per-database_access_permissions). Named databases have no creation/deletion surcharge; their operations/storage are usage-billed. No PITR, backup, TTL or always-on runtime is provisioned here. See [Firestore Standard pricing](https://cloud.google.com/firestore/pricing).

Grant only the trusted broker service account `roles/secretmanager.secretAccessor` and `roles/secretmanager.secretVersionAdder` on each explicitly configured secret. Do not grant project-wide Secret Manager access, secret administration, deletion or version-manager rights. The two predefined roles can be granted at secret scope; a custom add-only role can omit the predefined adder's rotation permission. See [Secret Manager access control](https://docs.cloud.google.com/secret-manager/docs/access-control) and [role permissions](https://docs.cloud.google.com/iam/docs/roles-permissions/secretmanager).

The broker also needs Firestore entity get/update permissions; the explicit enrollment operator additionally needs create. Scope IAM to the selected database where supported and keep these rights away from provider task code. The REST endpoint allowlist is defense in depth, **not** a document-level IAM security boundary. IAM-authenticated Firestore access does not rely on application security rules; see [Firestore security rules and server access](https://docs.cloud.google.com/firestore/native/docs/security/rules-conditions). Provide `run.executions.get` for the configured job to verify acquisition and reconciliation. No job create/run/cancel permission is used by this adapter.

A root-owned Python file or environment cleanup alone does not isolate the broker from model-run project tools. The deployment must prevent task code from obtaining the broker's metadata identity, Firestore permissions, socket/service access, or private control files. A dedicated trusted broker service with authenticated narrow operations and a separately isolated worker is one deployment option; that service/API is **not implemented here**. Until this boundary and durable local-refresh handoff are integrated, do not enable real project execution using this adapter.

## Bounds and validation

Google requests have a 10-second socket timeout and a 15-second socket shutdown watchdog; platform DNS resolution remains a platform operation. Responses are capped at 128 KiB, control data at 16 KiB and credential bytes at 64 KiB. Errors contain fixed codes, never response bodies or credentials. No network retry, scheduler, background polling, always-on compute or cloud resource creation is added by this module.

Run `python -m unittest discover -s tests -p test_cloud_credential_broker.py -v`. Tests use synthetic opaque bytes and an atomic Google wire-schema simulator, with concurrent acquisition/commit and lost-acknowledgement faults. They verify safe recovery, blocked takeover, exact version/checksum handling, owner binding, endpoint restrictions, and sanitized errors. These tests establish local behavior; they do not prove deployed IAM, provider refresh compatibility or end-to-end connection.
