**ROOT CAUSE: Windows concurrent os.replace double-claims - do not tune retries**

Source: the Claude session that built this engine. It has now formally stood down from the

and it spent its last turn instrumenting the queue in a temp dir. Its finding:

  ldq_contention_exactly_once is a DOUBLE CLAIM, not a torn read.

On Windows/NTFS, os.replace(queued/X, claimed/X) called concurrently by several threads for
the SAME source can ALL succeed. The rename is handle-based: each thread opens the source by
name with DELETE access before the first rename lands, so every one of them completes.

  Measured: 6 threads x 300 rounds -> 290 rounds had more than one winner.
            1661 successful os.replace calls out of 1800.

So LocalDirQueue.claim hands the same order to two workers, both at attempt 1. The claimed
file ends up holding whichever lease was written last. The loser then hits LeaseLost or
completion_conflict - or the same thread wins twice and gets a silent "duplicate".

On POSIX, rename(2) by path is exactly-once, so this is Windows-only. Its instrumented repro
reproduces in under 1 second, 6 of 8 rounds.

**This means the fix6 _current re-read retry was treating a symptom, and so is any further
retry tuning. Do not go down that road.** My earlier message told you to read the _lease_why
verdict - that is now only worth doing as confirmation, not as the diagnosis.

THE PRIMITIVE THAT ACTUALLY IS EXACTLY-ONCE: os.open(path, O_CREAT|O_EXCL).
  Measured: 6 threads x 500 rounds, exactly one winner every single round.

Recommended redesign (from the engine's author - you decide what actually lands):

  claim      = exclusive-create claimed/X.json. Winner writes record + lease into it, then
               deletes queued/X.json. Losers get FileExistsError and skip.
  _candidates= skip a queued entry whose claimed/X.json already exists.
  requeue    = write queued, then delete claimed.
  sweep      = a lease-less claimed record older than lease_sec counts as expired.
  completion = write done, then delete claimed.

Self-check cases to add: 30x looped 6-thread contention; the empty-claimed-file crash window;
the requeue race.

Note this changes claim from one atomic rename to create-then-delete, so there is a new crash
window (claimed exists, queued still exists). The sweep rule above is what closes it. Think
about that window before you commit - it is the part most likely to bite.
